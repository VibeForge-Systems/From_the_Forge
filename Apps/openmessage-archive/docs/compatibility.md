# Compatibility matrix

This file records **what has been tested**, not what is expected to work.
Research findings and expectations are in
[supported-formats.md](supported-formats.md). A cell only changes to
"Supported" after a test proves it, whether automated, against a synthetic
fixture, or a recorded manual test on real hardware.

Legend: **Supported**: tested and working. **CI**: built and unit-tested in
CI, not exercised by hand. **CI (synthetic fixtures only)**: exercised by
automated tests against the committed synthetic backups in
`tests/fixtures/backups/`, **not** against a backup made from a real device.
**Untested**: expected to work but not yet verified.
**Planned**: not
implemented. **Unsupported**: deliberately out of scope, and detected and
reported when encountered.

**Synthetic-fixture tests are not real-device tests.** The fixtures are
generated by `scripts/fixtures/make_synthetic_backups.py` from the same
reading of the format that the Rust code follows. Only the AES and PBKDF2
primitives (from the `cryptography` package) are independent of our code,
and the oracle run below cross-checks the encrypted layout against one
third-party implementation. A shared misreading of the format could still
pass every test here. Nothing in milestone 2 has been run against a backup
made by Apple Devices, iTunes, Finder or `idevicebackup2` from a real
iPhone.

**The same holds for milestone 3.** The extraction check has been run only
against the synthetic messages catalogue in `tests/fixtures/messages/`,
which is generated from our own reading of the sms.db format, and against
two third-party sample databases (oracle run 4), both of which are macOS
`chat.db` files, not iOS sms.db. No backup made from a real iPhone has been
checked, so every readable result from a real backup carries the
qualifier "This iOS version has not been tested" (a damaged, unsupported or
incomplete result does not repeat it). No column profile in the catalogue
is an iOS version.

### Milestone 2 headless smoke test (Linux container, not a desktop)

On 2026-10-18 the release binary (`npx tauri build --no-bundle`) ran under
Xvfb in a Linux container, driven with `xdotool`. Settings were pre-written
with an archive folder and one added parent folder holding copies of the
`plain`, `enc`, `incomplete` and `bomb-info` fixtures, because the GTK
folder picker cannot list directories without D-Bus. Observed:

- The Backups page (reached with Ctrl+3) listed four backups with the
  states Ready to check, Encrypted, Incomplete (with the raw SnapshotState
  in the reason) and Ready to check (`bomb-info`, whose details came from
  Manifest.plist's Lockdown).
- Validating `plain` ran over the IPC channel and showed an importable
  report; `.oma-staging` was empty afterwards.
- Unlocking `enc` with a wrong password reopened the password dialog with
  the error; the right password produced an importable report; `.oma-staging`
  was empty afterwards.

This exercises the CSP, the capability grants and the channel wiring. It is
not a manual test on a real desktop, and it does not cover the folder
picker. The manual checklist below has not been run.

`extractionFinished` event and the report fetch in the real webview. It is
not a manual test on a real desktop, it did not observe the staged sms.db
while it existed (each check took a few milliseconds), and it does not
replace the manual checklist for milestone 3 below, which has not been run.

## Manual checklist for milestone 3 (not yet run)

Record each run here only once it has actually been done, with the date,
the operating system and, for a real backup, the iOS version, the device
model and how the backup was made. The milestone 2 checklist below is still
open as well.

**Linux (Ubuntu 26.04.1, real desktop):**

1. Add a parent folder holding copies of `msgs-full-plain`,
   `msgs-full-enc`, `msgs-wal-plain`, `msgs-attachments-enc`,
   `msgs-corrupt-plain`, `msgs-vtab-plain` and `msgs-unsupported-plain`,
   taken out of the repository (move each backup folder up one level).
2. Run the extraction check on each. Confirm the outcome and its
   qualifiers match `<name>.expected/report.json`, that every qualifier has
   its own sentence, and that a count the database does not record reads
   "not recorded", never 0.
3. On `msgs-full-enc`, enter a wrong password, then the right one. Confirm
   the dialog's wording for the extraction check (the headless run saw
   "Unlock and validate").
4. Cancel a check during each phase you can catch (use a larger synthetic
   database, such as the one `perf_synthetic_large` builds, wrapped in a
   backup), and confirm `.oma-staging` is empty afterwards.
5. While a check runs on a large database, list
   `<archive>/.oma-staging/s*/db/` and confirm the staged `sms.db` is there
   with mode 0600 in a 0700 directory; confirm it is gone when the check
   ends.
6. Kill the app (`kill -9`) while a check on a large database is reading
   rows. Confirm the plaintext copy is still on disk, then start the app
   again after 5 minutes and confirm the sweep removed it.
7. Confirm that no message text, address, chat name, GUID or file name
   appears in the window, and none in the log with `OMA_LOG=debug`.

**Windows 11:** the same steps, plus:

- **Staging removal with Defender active.** With real-time protection on,
  run the check on `msgs-full-enc` several times and confirm `.oma-staging`
  is empty afterwards and the report says the copy was deleted. Record any
  retry or failure to remove.
- **File attributes.** While a check runs on a large database, confirm the
  staged `sms.db` and `sms.db-wal` carry the temporary and
  not-content-indexed attributes (`attrib` or `Get-Item … | Select
  Attributes`).
- **WAL on Windows.** Confirm `msgs-wal-plain` reports the `-wal` as copied
  and counts 7 message rows, which needs the staged `-wal` to be read on
  Windows (UNVERIFIED until run).
- The release build: `npm run tauri build`, install the NSIS package, and
  run one check.

**Real backups** (one unencrypted, one encrypted; from a current iOS),
**run in the app**, which stages the decrypted copy only inside the archive
folder. Do not use the `external_sample` test harness for a real backup: it
copies the whole backup into the system temp folder and stages there.
Record:
record the iOS version, the model, the outcome, each qualifier, the counts
of unknown tables and columns, the missing expected columns (by name, from
the closed list), whether a `-wal` was listed, the check's duration, and
answers to hardware questions 19–28 in supported-formats.md where the
report gives them. **Record counts and kinds only; never commit anything
from a real backup**, and never record message text, addresses or names.

## Manual checklist for milestone 2 (not yet run)

Record each run here only once it has actually been done.

**Linux (Ubuntu 26.04.1, real desktop):**

1. Add a parent folder holding copies of the `plain`, `enc`, `incomplete`
   and `bomb-info` fixtures, taken out of the repository. Check each state.
2. Validate `plain`. Confirm the Validate note, and the sync warning with
   the archive folder inside a folder the sync heuristic matches.
3. Unlock `enc` with a wrong password, then the right one.
4. Cancel during "Checking the password", using `enc-slow`.
5. Confirm `.oma-staging` is empty afterwards and that no `sms.db` ever
   appeared in it.
6. Confirm the added folders survive a restart, then Forget a folder.
7. Kill the app during a job (`kill -9`), wait 5 minutes, start it again,
   and confirm the leftover session is removed.
8. Choose an archive folder on a FAT or exFAT USB drive, automounted with
   default options, and confirm Settings marks it unusable (the `private`
   check). Remount with `dmask=077,fmask=077` and confirm it is accepted
   and a check runs.

**Windows 11:** the same steps, plus default-location discovery with Apple
Devices, desktop iTunes, or both, and with iMazing's default location
(confirm that `iMazing.Versions` is not listed, and that an archive folder

path of about 200 characters; whether WebView2 offers to save the password;
a `finished` event over 8 KiB arriving in `tauri dev`; staging removal while
Defender is active; which open mode the staged WAL-mode Manifest.db gets
(`ReadOnly` or the `ReadWriteQueryOnly` fallback; the `plain-wal` test
prints it).

**Real backups** (one unencrypted, one encrypted; made by Apple Devices,
iTunes or `idevicebackup2` from a current iOS): record the iOS version, the
model, the measured key-derivation time, the DPIC and ITER values (numbers
only), the keybag notes reported, the `blob-sizes` count, and the answers to
the open questions in supported-formats.md (SnapshotState values, WAL files,
